RoboCerebra: our HPP segment policy against the published baselines

long-tamp · #159 / #160 / #163 / #186 / #187 · 31 Oct 2026 · Ideal setting only on our side

Run like the published methods, each task in one uninterrupted rollout and scored with the paper's Eq. 1, our HPP policy completes 67.7 % of the Ideal tasks' key state changes (row C). The best published method, SparkVLA, scores 46.4 %, and the best published run that is handed the ground-truth plan scores 31.2 %. Handed to long_tamp.mission as one goal a rollout (row D), with the step budget shared over the rollout and failed steps replanned, it completes 67.9 %. With the benchmark's resume before every segment (row A) the policy passes 79.3 % of segments; that is an upper bound, not a score. None is a like-for-like win. Our policy reads the simulator's exact object poses and is given each subtask's goal; the VLAs see only camera images. Read the numbers below as "what a model-based planner reaches with privileged state", not as a leaderboard entry.

1 · Ideal-setting success

Every bar is a success rate in % on the Ideal setting, the only one we have run. The published bars use the paper's Eq. 1: the share of each task's key object-state changes that hold. Our bars count benchmark segments, a close but not identical unit (see §4). The grey line marks the replayed human demonstrations, which complete 73.7 % of subtasks (56 of 76). That is a reference point, not a hard ceiling: even the recorded demonstration states miss some of their own goals, and a policy scored per segment can complete subtasks the demonstration missed.

2 · Every setting

RoboCerebra has six settings: Ran. (random disturbance), Obs. (observation mismatch), Exp. and Exe. (memory exploration and memory execution), Mix, and Ideal (no disturbance, the easiest). For the planner + VLA rows and the ground-truth-plan rows, Ideal is the best or near-best setting, and Exp. or Mix is the worst. The memory-aware methods (Mem-0, SparkVLA) do best on Exp. instead. Our planner has run only Ideal. It plans each segment from the scene as it stands and, uninterrupted (row C), replans within the segment's budget when a plan leaves the segment undone; how that holds up under disturbance is still to measure. Treat its cells as Ideal-only numbers, not as an average.

3 · Where our segments go

Row A, with the resume. The 10 Ideal cases × 10 seeds give 760 segments. Each bar splits one case's segments into those that passed, those that failed, and those the policy declines. Declined goals are open, turnon, On over an object, and regions the exported scene lacks. The VLAs attempt every segment, so the honest headline counts declined segments as failures (79.3 %). Counting only supported segments gives 84.9 %; that answers a different question.

5 · Which comparisons hold up

Reasonable, with caveats

Ours, row C (67.7 %), against the ground-truth-plan runs (26.6–31.2 %). Both sides are given the plan and run each task through, so the remaining gap comes from the controller. Ours still has exact state, so treat 67.7 % as what a state-based planner reaches, not as a matched score.

Not fair

Ours against SparkVLA (46.4 %), HPE (21.1 %) or any VLM-planner row. Those systems work out the plan from language and pixels. Ours is given the plan and the true poses. Beating them on Ideal says nothing about the harder problem they solve.

Not comparable

Row A's 79.3 %, 84.9 % (supported segments only) or 69 % (rollout success) against anyone. All three resume before every segment, so an early failure never carries on. The second also leaves out 7 % of segments; the third uses the benchmark's all-done flag after resumes have already marked earlier steps done: case3 and case10 succeed on every seed with a fifth or more of their segments failed.

To make the comparison fair

  1. Run uninterrupted episodes. Done: row C drops resume(k), chains the segments and scores with Eq. 1 (67.7 %). Row D plans the whole task as one mission (67.9 %), with the step budget shared over the rollout.
  2. Count every declined segment as a failure, or add the missing skills (open, turnon).
  3. Run all six settings, so there is an Avg to set beside theirs. Ran. and Obs. need replanning when objects move.
  4. Add a perception-in-the-loop variant that estimates object poses from the cameras instead of reading the simulator. That would make it a matched comparison with the ground-truth-plan rows.
  5. Check the † numbers against the paper's PDF before citing them.
